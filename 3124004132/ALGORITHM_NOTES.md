# 算法调整记录

## 第一版跑得快，但结果有点离谱

第一版直接把一元、二元字符频次放进余弦相似度。代码不复杂，处理一篇一万字左右的文本只要约 30 毫秒，我原本觉得这个方案应该够用了。

真正拿文本一跑才发现问题：增加、删除和调序后的结果几乎都在 `0.99` 左右。这个分数看起来很高，但没有把文本实际发生的变化体现出来。

| 改写类型 | 第一版结果 |
| --- | ---: |
| 增加内容 | `0.9928` |
| 删除内容 | `0.9934` |
| 轻度调序 | `0.9987` |
| 中度调序 | `0.9953` |
| 较明显调序 | `0.9887` |

仔细想了一下，原因其实不难理解。整篇文章很长，即使中间增加或删掉一部分字，常用汉字的整体频率还是差不多。余弦相似度擅长比较两个向量的方向，却不太在意一边到底多了多少内容。一元字符又不记录顺序，所以调换位置后分数也几乎不变。

## 第二版加入覆盖率和三元特征

我没有把第一版全部推翻，而是保留余弦相似度作为辅助，再加入特征覆盖率。覆盖率的思路比较直接：统计两边真正重复的特征数量，再除以特征更多的那一边。这样增加和删除内容都会拉低结果。

目前采用的组合是：

- 一元字符权重 `0.75`，主要看内容保留了多少。
- 二元字符权重 `0.20`，补充相邻字符关系。
- 三元字符权重 `0.05`，对更明显的局部调序更敏感。
- 覆盖率占最终结果的 `0.80`。
- 余弦相似度占最终结果的 `0.20`。

这里没有只用二元或三元特征，是因为随机插入一个字会同时破坏附近多个连续片段，分数容易一下掉得太多。一元特征保留较大权重，可以让算法对小范围修改更宽容一些。

## 调整后的结果

| 改写类型 | 第一版 | 第二版 |
| --- | ---: | ---: |
| 增加内容 | `0.9928` | `0.8205` |
| 删除内容 | `0.9934` | `0.8082` |
| 轻度调序 | `0.9987` | `0.9831` |
| 中度调序 | `0.9953` | `0.9447` |
| 较明显调序 | `0.9887` | `0.8922` |

增加和删除后的结果不再无条件接近 `1.00`，不同程度的调序也有了逐步下降的趋势。轻度调序仍然很高，是因为文章使用的字符和大部分局部片段都还在，我认为暂时可以接受。

第二版刚完成时，带着临时分析脚本处理同一批文本大约需要 67～81 毫秒。后来正式用 `cProfile` 定位并减少重复的文本规范化和向量校验后，查重函数的 30 次平均耗时从 `39.755 ms` 降到 `22.183 ms`，五组结果保持不变。详细过程放在 [PERFORMANCE_REPORT.md](./PERFORMANCE_REPORT.md)。

这组权重不是“唯一正确答案”。后面还要继续检查短文本、完全无关文本和混合中英文等边界情况。如果发现某一类文本明显不合理，再记录原因并调整，而不是为了让某一个结果好看就单独写特殊判断。
