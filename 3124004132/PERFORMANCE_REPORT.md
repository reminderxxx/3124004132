# 性能分析与优化记录

## 为什么还要做性能分析

程序处理一万字左右的文本本来就没有超过 5 秒，但“跑得动”不代表没有重复工作。作业要求使用性能分析工具，我也想看看自己的直觉准不准，所以先保存优化前的数据，再根据结果改代码。

测试环境为 macOS、Python 3.9.6。基准样例使用老师给出的原文和增加内容版本，计时只统计 `calculate_similarity()`，先预热一次，再连续运行 30 次。不同电脑上的绝对耗时会有差异，这里主要比较同一环境下的前后变化。

## 第一次 profile：我猜错了热点

我一开始以为最耗时的是 Unicode 规范化和移除标点，实际跑 `cProfile` 后，最大的重复开销却是 `_validate_feature_vector()`。

优化前的主要数据如下：

| 指标 | 优化前 |
| --- | ---: |
| 函数调用次数 | 783,388 |
| 单次 profile 总耗时 | 0.071 s |
| `calculate_similarity()` 累计耗时 | 0.065 s |
| `_validate_feature_vector()` 调用次数 / 累计耗时 | 8 次 / 0.027 s |
| `normalize_text()` 调用次数 / 累计耗时 | 8 次 / 0.011 s |
| 30 次平均耗时 | 39.755 ms |
| 30 次中位数 | 39.637 ms |

问题出在组合算法需要分别计算一元、二元、三元覆盖率，最后再算一次余弦相似度。公开函数每次都会完整检查两个特征向量，而这些向量其实刚由程序自己生成；另外已经规范化的文本传入 `extract_features()` 后，又被规范化了一遍。

## 这次怎么改

我没有修改权重和相似度公式，只把内部已确认安全的计算路径拆出来：

1. 原文和抄袭版各规范化一次，内部直接从规范化结果提取三种 n-gram。
2. `cosine_similarity()` 和 `feature_overlap()` 继续保留完整校验，供外部直接调用。
3. `calculate_similarity()` 使用内部计算函数，不再重复校验自己刚生成的特征。

这样改的好处是公共接口没有变，错误输入仍然会被拦住，测试也不用为了优化而降低要求。

## 优化后的结果

| 指标 | 优化前 | 优化后 | 变化 |
| --- | ---: | ---: | ---: |
| 函数调用次数 | 783,388 | 254,400 | 减少 67.5% |
| 单次 profile 总耗时 | 0.071 s | 0.033 s | 减少 53.5% |
| `calculate_similarity()` 累计耗时 | 0.065 s | 0.029 s | 减少 55.4% |
| `normalize_text()` 调用次数 | 8 | 2 | 减少 75.0% |
| 30 次平均耗时 | 39.755 ms | 22.183 ms | 减少 44.2% |
| 30 次中位数 | 39.637 ms | 22.125 ms | 减少 44.2% |

优化后的主要耗时变成 `_extract_normalized_features()`，它需要实际遍历文本并生成 n-gram，这部分属于算法本身要做的工作，暂时没有继续为了几毫秒增加更复杂的结构。

五组示例的结果仍然是 `0.8205`、`0.8082`、`0.9831`、`0.9447` 和 `0.8922`。同时重新执行了 71 个测试、分支覆盖率和 Ruff 检查，结果分别是全部通过、100% 和零警告。
